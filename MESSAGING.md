# Private messaging, media and moonlit UI — 2026.11.19.2

This release extends the existing Flask/SQLite/browser and React Native app. No new external service is required. The root Python files are authoritative; use `tools/build_release.py` to regenerate `release/` and both Solace ZIPs. `messaging.py` is included in the server allowlist, Docker build, startup tests and PythonAnywhere archive.

## Implemented behavior

- Empty room names use the saved display name, for example “Peach’s room”; first-time visitors can still choose a name. Public visibility requires confirmation. Hosts can rename rooms later.
- Friend codes are eight uppercase characters, displayed as `ABCD-EFGH`. Input ignores case, spaces and the separator; confusing `0`, `1`, `I`, `L` and `O` are excluded. SQLite enforces uniqueness. Older codes remain aliases so existing links can still identify a profile. Codes never authorize account access. Connections remain attached to the same identity during guest upgrades.
- Friends has an explicit preview before requesting, pending/accepted/declined/blocked states, self/invalid/duplicate feedback, a copy action and a Message button. A rejected request has a 60-second minimum cooldown. Requests and lookups are rate limited; circles remain capped at 100 connections/requests.
- Recognized identities go directly to Home. Private app pages have a shared sidebar on desktop and compact mobile navigation. No duplicate Open Solace button appears there. Public informational pages offer Go to home for recognized users. Home, Friends, Rooms, Settings, Messages and Games use separate screens. The moonlit colors, rounded panels, landscape theme cards and game finish follow the supplied references using lightweight local SVG/CSS artwork.
- One persisted conversation exists per accepted-friend pair. Existing conversation history is readable after unfriending, but new sends require acceptance. A block denies conversation reads/sends/media to both parties. Own-message/attachment erasure and inbox hiding remain owner-authorized actions even when blocked. Guests use the existing signed, unguessable browser identity. Clearing browser data may lose access; registering in the same browser preserves chats and attachments. Signing into a different existing account does not merge identities.
- Private text and media use bounded one-second foreground polling; inbox previews/unread counts refresh every five seconds. Message history pages contain 50 messages; inbox pages contain 30 conversations. Typing expires after five seconds. Read markers never go backwards, and read receipts display only when both accepted friends opt in. Online status follows the existing friend-only opt-in setting.
- Sends use stable per-sender request identifiers and server uniqueness constraints. Lost replies can be retried without duplicate messages. Failed sends retain their draft and have Retry/Discard controls; typing the next draft while a previous send completes does not erase it. Unsent drafts are memory-only and are not guaranteed after closing/reloading the page.
- Deleting a conversation hides only the current user's inbox copy; the other participant is unaffected. A new incoming message brings it back. Explicitly opening it again from Friends restores its history. Removing a sent message creates a tombstone for both participants and clears its attachment. Inbox hiding alone does not free stored message/media quota.
- An optional watch invitation creates a private room and uses the existing friend invitation system. Chat stays usable independently; it does not force navigation into the room.

## Media and privacy

Pictures and GIFs can be attached in room chat and private messages. The picker previews locally, reports progress, supports cancellation, retries and shows server validation errors. Attachment-only room messages work. GIFs are sent as real re-encoded animated GIFs; the default display is a still poster with explicit Play/Pause controls. Expanded images use an accessible dialog. Native room chat has attachment/viewer entry points and protected thumbnail rendering with an expanded web-view fallback.

The server accepts JPEG, PNG, still WebP and GIF by decoded content, up to 8 MiB input and 16 megapixels. Animated files must be GIF, with at most 180 frames, 40 million decoded pixels and two minutes. Static output is resized within 1600×1600; GIF frames within 800×800. Metadata is removed; static output is JPEG. Encoded data plus poster cannot exceed 8 MiB. One decoder at a time per worker bounds decode concurrency; busy uploads receive a retryable response. Pillow 13.0.0 or newer is required.

Uploads are charged to the existing per-user quota alongside profiles, private text and history. Admin quota overrides still apply. Room text and operations backups remain separate accounting. Canceled/lost-response uploads that reach the server can remain staged for up to 24 hours; run the existing hourly maintenance job to remove expired unsent uploads. Sent room media is deleted with the room. Deleted BLOB space is reusable SQLite space; logical quota release does not imply an immediate smaller database file.

All media access checks current identity and room/conversation permission; staged files are visible only to their uploader. URLs contain opaque identifiers and are not access credentials. Owners can remove their files, and room hosts can moderate room attachments. Private responses use no-store/noindex. Private message text/media stays in the main SQLite database and its restricted backups, not the operations chat archive, analytics or routine logs. This is server-authorized privacy, **not end-to-end encryption**; the database operator can access stored data. Account deletion clears the deleted user's private-message bodies and media. Other participants retain their own sent messages. Private messages otherwise persist until removed; inbox hiding is not erasure.

Media metadata revisions omit unchanged attachment lists from new-client room polls. Clients retain the permitted metadata only within the same room/storage generation. Existing displayed media nodes are reused when room text updates, avoiding repeated image downloads and GIF resets. Older clients that do not send a revision continue receiving the full bounded list.

## Deployment and verification

1. Back up the persistent instance with the supplied storage tool. Backups contain private conversations and images and need restricted access.
2. Upload the complete PythonAnywhere ZIP contents, including `messaging.py`, changed Python files, templates and static assets. Keep `instance/`, saved secrets, databases and provider keys. Install the pinned requirements in the app environment and reload all workers together. Additive migration 5 creates messaging/media tables and the read-receipt preference. Do not copy a release database over existing data.
3. The included Waitress entrypoint allows an 8 MiB multipart upload plus overhead while Flask retains small JSON limits. Configure any actual proxy/CDN request limit and timeouts accordingly. PythonAnywhere's effective plan-specific upload/storage limits must also permit the chosen size.
4. Schedule `python tools/maintenance.py --instance /absolute/instance/path` hourly. The tool clears expired staged uploads without deleting sent private messages.
5. Rebuild standalone Android/iOS apps for native attachment entry points. The iOS configuration includes photo-library and camera purpose text for user-initiated picker choices, following the [official React Native WebView upload guide](https://github.com/react-native-webview/react-native-webview/blob/master/docs/Guide.md#add-support-for-file-upload). No GIF search provider was added; direct GIF upload is independent of credentials.

Verification results are in `audit-results/messaging-verification.json`. Tests use disposable local databases, synthetic media and separate browser identities. Physical phones are unavailable. Native cookies, OS pickers, background behavior and long physical-phone sessions remain unverified. The prior production-domain, operator/legal, SMTP and dependency limitations in LAUNCH-READINESS.md still apply; this feature update is not an unrestricted public-launch certification.

Rollback uses matching pre-update code and a verified instance backup restored into a new directory while workers are stopped. Restore revokes account sessions, short-lived native handoffs, private invitation links and typing indicators. It does not publish conversations or copy credentials into the release.
