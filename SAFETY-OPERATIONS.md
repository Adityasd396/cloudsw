# Open World, safety and operations — 19 November 2026

Root source is authoritative. Production starts `app:app` through `serve.py` (Waitress) or the configured PythonAnywhere WSGI file. `release/` is generated by `tools/build_release.py`, not a second source tree. No production data or deployment was accessed for this work.

## Owner setup

1. Back up **both** SQLite databases using `python tools/storage.py backup --instance /absolute/instance --output /private/new-backup-folder` (see `python tools/storage.py --help` for subcommand options). Keep the existing server secret separately. Backups include private messages/media, reported evidence and staff authenticator secrets. Restrict access, encrypt storage/backups outside the application and set a rotation policy.
2. Upload the entire PythonAnywhere ZIP into the existing code directory, preserving `templates/` and `static/`. Keep the existing `instance/`, server secret and environment settings. Install `requirements.lock` in the app's virtual environment. Additive migrations 6–7 run on import; fresh and legacy startup are tested. Do not copy a local instance or test credentials to the host.
3. In the same configured environment as the server, run `python setup_staff.py your.individual.username`. The first staff identity must be an administrator. Enter a unique password of 14–128 characters and enroll the displayed URI in an authenticator. The URI is a secret: do not paste it into chat, logs or a ticket. Each staff member gets their own identity. Enroll additional identities with `--role moderator` or `--role operations`.
4. Reload the server and verify `/ops/solace` over HTTPS. Use the named username, password and current authenticator code. MFA uses RFC 6238 SHA-1, 6 digits, 30-second steps, one-step clock tolerance and persisted replay prevention. Set correct server/device clocks. No SMS, push notification or device-permission request is used. [RFC 6238](https://www.rfc-editor.org/rfc/rfc6238.html).
5. The first named enrollment disables legacy shared-password sign-in and legacy admin cookies. The old owner bootstrap remains available before enrollment to preserve access, but is **not sufficient for a public launch**. New safety actions always require named staff. Sessions last 30 minutes, use HttpOnly/SameSite Strict cookies scoped to the existing dashboard, and are Secure over HTTPS. Changing staff access revokes that identity's sessions. The last enabled administrator cannot be disabled or demoted through HTTP.
6. Keep at least two individually controlled administrator identities and a restricted offline backup. There is no email-based staff MFA recovery or HTTP enrollment/reset endpoint. Recovery requires the server operator's local access and a newly enrolled administrator; disable the lost identity after recovery. Filesystem operators already control the application, database and secrets.

Required existing configuration: `SOLACE_ENV=production`, stable `SECRET_KEY` or existing instance secret, `SOLACE_PUBLIC_URL=https://your-real-host`, a real `SOLACE_CONTACT_EMAIL`, HTTPS and the documented trusted-proxy settings. Configure SMTP for account recovery/verification and `YOUTUBE_API_KEY` for provider search. No external service or new secret is required for discovery, direct GIF uploads, reports or TOTP. Never put staff passwords, SMTP passwords or API keys in client code. `.env.example` has no real credentials.

## Discovery and profiles

Open World is separately **off by default**, including for all existing users. Friend presence sharing does not enroll a profile. Users choose online visibility, discovery avatar sharing and limited stats separately; optional bio/interests are plain text. Discovery shares session count and watch duration only when selected, never precise activity times or private history. Leaving discovery removes all its leases immediately.

A visible document renews a 32-second presence lease every 15 seconds. Hiding/leaving removes its lease; network loss or a killed process expires it within 32 seconds. Other active tabs remain visible. At most eight leases per identity are active. Account leases are bound to a currently valid account-session hash; account upgrade clears old guest leases. Stale account sessions cannot advertise presence. Guest identities survive browser visits and upgrades, but clearing browser data or creating a new identity can evade identity-based restrictions. No permanent anonymous-ban guarantee is made.

Listings return at most 12 profiles with a five-minute, viewer-bound signed cursor, scanning at most 100 candidate rows per page. Profile cards use existing friend codes, connections and blocks. Public codes identify profiles and do not authorize account access. Profile fields and avatars are filtered on the server. Known friend codes can still be previewed when discovery is off; discovery itself never appears in search indexes. Existing friendship acceptance is required for direct messages and media. A declined request has a persistent 24-hour cooldown, even after dismissing it.

## Reports, moderation and privacy

Profiles/users, direct messages, room messages, attachments, rooms and invitations can be reported. The server verifies access to the source and captures a bounded snapshot; client evidence is not treated as authoritative. Private source bodies do not appear in report queues, inventories, routine logs or analytics. Attachment evidence contains metadata/hash and a sanitized poster only when at most 64 KiB, not an original-file archive. Snapshots survive original deletion until evidence expiry. Submission is idempotent for reporter/type/reference and uses identity and IP budgets. Reports alone never trigger punishment. A reporter can immediately block using the existing block behavior, which also separates shared rooms.

Evidence expires after 30 days. Minimal case metadata, explanations, notes and appeals expire after 180 days. Hourly request cleanup and `python tools/maintenance.py --instance /absolute/instance` enforce retention; schedule maintenance daily, including when the service is idle. Old backups require independent rotation. Evidence review requires a permitted named identity, a case ID and a confirmed investigation reason; each read is audited. Staff must avoid copying private content into routine action reasons. Reporters receive only their own case status, not confidential investigation details.

The existing `/ops/solace` contains case queues, severity, named assignment, notes/resolution, justified evidence review, appeals, community inventories, staff roles, restrictions and action history. Inventories expose operational metadata, not message bodies, private media URLs, emails or IP addresses. Private room names are redacted there; inventories omit friendship/message/invitation participant associations and expose non-joinable room references instead of private room codes. Named operations sessions receive aggregate health data instead of unrestricted visitor/IP/diagnostic lists. Unrestricted room-chat exports are disabled after named enrollment. New room-chat archiving is disabled by default; the legacy archive fixture/explicit server configuration `SOLACE_ROOM_ARCHIVE=True` can opt in for a defined lawful operational need. Previously retained archives still follow 30-day cleanup. Direct messages are excluded from operations archives.

Administrator permissions are complete. Moderators can review reports/evidence/appeals, warn/mute/restrict, remove content and close rooms; permanent bans, emergency switches and staff management require additional permissions. Operations staff get health/storage summaries and action audit access. Additional grants are explicit, server enforced and individually attributable. Broad/destructive actions and existing named-staff storage/gesture changes require confirmation and a reason. Host room moderation remains separate from platform moderation.

Warnings appear in Safety & appeals. Mutes block new room and direct messages. Feature restrictions apply to discovery, messaging, uploads, invitations, room creation, connections or games. Suspensions/bans block app activity, revoke account sessions, remove room membership (with normal host transfer/cleanup) and remove discovery leases. Existing polling detects restrictions; web playback is stopped and the native player unmounts. Revoked guest sessions return an explicit session-ended response and require a new profile or sign-in. Owners can review restrictions and appeal; authorized account owners retain data-management routes. Accepting an appeal records a decision; staff explicitly reverse eligible restrictions so the action is independently audited. Guest session revocation records the old identity in a minimal revocation ledger. Existing and copied guest cookies lose profile authority on their next request, alongside lease/membership removal. The ledger retains only identity and revocation time until operator archival; it does not make a newly created anonymous identity permanently bannable.

Audit rows contain actor, target, action, reason, timestamp and outcome. Main-database actions and their audit event commit together. SQLite triggers reject update/delete of audit rows, and HMAC links detect alteration using the existing server secret (`/ops/solace/safety/audit` verifies the chain). This is **not external immutable storage**: a database operator can remove triggers, and an operator with the secret can rewrite the chain. Preserve the server secret when restoring; otherwise historical HMAC verification fails. Staff-role changes span the operations and application databases, so an audited intent precedes the change and an outcome follows; a crash can leave an unresolved intent. No cross-database atomicity or independent timestamp authority is claimed. Audit events are retained until the operator archives the instance securely.

## Emergency switches and abuse limits

All switches persist in the main database and take effect on the next request:

| Switch | Behavior |
|---|---|
| Registrations | Blocks new account signup; existing sign-in and account recovery remain available. |
| Guest access | Blocks guest room activity and new guest profile setup. Affected room polling removes guest membership/leases. Own history and appeal access remain available; sign-in remains possible. |
| Discovery | Blocks listing/active presence and new opt-in changes; leaving discovery remains possible. Friend-only sharing stays separate. |
| Room creation | Blocks new rooms, preserves existing playback/chat. |
| Invitations | Blocks new invitation actions/redemption and link regeneration. Existing room codes remain usable; link revocation remains available. |
| Messaging | Blocks new room/DM messages and typing writes; existing messages remain readable and deletable. |
| Uploads | Blocks new uploads; existing authorized media remains readable/removable. |

New reports: six/hour/identity and 12/hour/IP, duplicate receipts included in request budgets. Discovery lists: 60/minute/IP; profile previews: 60/minute/identity plus 120/minute/IP. Presence: 180/minute/IP plus eight active tabs/identity. Room chat: 60/minute/identity and 180/minute/IP. Existing friend, invitation, authentication, media and DM limits remain. Identity buckets no longer reset when the IP changes. Staff login uses both username and IP-signal budgets (five failures/15 minutes), generic failures, expensive password hashing and TOTP replay prevention. Shared IPs are temporary rate signals, never proof of identity or an automatic permanent-ban trigger.

SQLite-backed counters, switches, restrictions and room state are shared by workers using the **same local database files**. This does not support independent SQLite copies or multiple hosts. Use one deployment instance until external shared state is designed and measured. Waitress's existing thread/connection/payload/time limits remain; uploads have a bounded decoder per worker. Read polling is not a DDoS defense. Apply reverse-proxy/CDN connection and request budgets, a body limit consistent with the validated 8 MiB upload envelope, timeouts, TLS, bandwidth limits, upstream health alerts and restricted direct-origin access appropriate to the host. PythonAnywhere controls must match its supported configuration; do not blindly trust client-supplied forwarded headers. No complete attack-prevention or capacity guarantee is made.

Monitor availability/readiness, HTTP 5xx, 429 trends, latency, disk space, SQLite busy errors, client playback failures and staff authentication events. Request IDs and numeric reliability telemetry remain available; private message bodies, media URLs, credentials and tokens stay out of routine request logs. Named investigations use the separate evidence path.

## Release, rollback and evidence

Build with `python tools/build_release.py --version 2026.11.19.3`. The server ZIP must include `messaging.py`, `people.py`, `platform_safety.py`, `staff_auth.py`, `setup_staff.py`, all templates/assets and existing modules. The builder checks source/release/ZIP bytes and excludes instance data, credentials and the old private film. New migrations are additive; do not run an old server against the changed instance as an assumed rollback. Quiesce traffic, restore the pre-upgrade verified backup into a **new** instance directory and restore matching old code/secret. Restore clears account/admin sessions, pending invitations/handoffs/typing/discovery leases and changes the storage generation. See DEPLOYMENT-RELIABILITY.md and tools/storage.py; test restoration before applying it to live data.

See `OPEN-WORLD-REQUIREMENTS.md`, `audit-results/safety-verification.json` and `audit-results/safety-measurements.json` for verification and limits. Browser engines and simulated keyboard viewports are not proof of physical iOS/Android reliability, battery behavior or a real three-hour mobile session. No public deployment, account inspection or production load test was performed.
