# Returning users, guests and room invitations — 2026-11-19

Implemented using Flask, SQLite, the existing browser screens and the native WebView player. No production service or user data was accessed.

## Behavior

- Identity is restored on the server before rendering. Saved guests and signed-in visitors go to `/home`; new visitors choose sign-in, registration or a guest name. Expired account authority is discarded and cannot access the old account's profile/history. Browser preferences remain local.
- Guests can edit their name/picture and view/delete their own history and daily activity. Pictures use the existing content validation, metadata removal and quota checks. Clearing browser data can lose guest access. Guest history retains the existing 30-day policy. Registering in the same browser upgrades the same identity, picture, history and connections; signing into a different existing account does not merge identities.
- Dashboard statistics use actual watch events: one session per room/playback instance, with consecutive visible decoded-playing samples no more than 25 seconds apart credited as time. Reconnects do not create another session. Empty states contain no invented people, rooms or viewing numbers.
- Friends require a code-based request and explicit acceptance. Recent companions remain separate. Remove, decline and block controls are available. Detailed history and email never appear in friend responses. Online status and aggregate stats are opt-in; avatars can be hidden. Connections/requests are bounded to 100 per person. Blocking removes connections/invitations and separates people who share a room; hosts also ban the blocked participant from that room.
- New and migrated rooms default to Private. Only deliberate Public rooms enter discovery. Hosts must confirm public visibility. Name, content label and capacity (2–100) are editable. Capacity is enforced against reserved room membership, including temporary reconnects. Host-only remove/ban/unban controls are in Room Settings.
- Public discovery exposes an opaque listing identifier, room name, self-selected content category and occupancy/capacity. It exposes no room code, media source, private link, participant identity or private activity. Listings refresh every 2.5 seconds while Home is visible; this is polling, not a new socket service. Existing rooms and player connections survive a visibility change.
- Room header/Room actions open a separate invitation/settings screen; playing media stays mounted. Accepted friends can be searched and invited. Recipients accept/decline from Home. Duplicate pending invitations are rejected. In-app invitations expire after 24 hours. Redeemed join destinations last 10 minutes and survive guest setup/sign-in/registration.
- Private links use random 256-bit secrets in URL fragments, stored only in the private database and exchanged by CSRF-protected requests. Hosts can revoke/regenerate them; old link grants and pending invitations are invalidated immediately. A link otherwise lasts until revoked or the room closes. Room codes are an independent access method: revoking a link does not change a code someone already knows. Bans/blocks and capacity still apply to code joins.
- Native Home uses the same real dashboard. A CSRF-protected, 30-second, hashed, single-use exchange transfers identity between the trusted app WebView and native requests. Account handoff also checks the originating unexpired account session. No raw cookie or long-lived session token is sent through the bridge. Native invitation sharing uses the OS share sheet. Public invitation links open the web flow; native universal/app-link association needs a chosen production domain and signed builds. A new standalone app build is required for native changes.

## Deployment and data

No new service credentials are required. Migration 4 adds guest pictures, privacy settings, connections, blocks, room settings, bans, invitations and short-lived native handoffs. Existing data is retained. Keep the stable secret and persistent `instance/` directory. Upload the complete PythonAnywhere bundle, install its pinned requirements in the app environment, and reload all workers together. See PYTHONANYWHERE.md and PUBLIC-LAUNCH.md for HTTPS, production domain, SMTP and operator details.

Back up the instance before updating (`python tools/storage.py --help` describes backup/restore). Use the existing verified backup tool; the new records are inside the same room database. Restore revokes native handoffs and private invite links/pending invitations as well as account sessions; hosts must create fresh links. To roll back, stop workers and restore the matching pre-update code and instance backup into a new directory, then point the application at that directory. Do not copy a release over live databases, replace the saved secret, or restore an older database while workers are running. Backups contain private guest pictures and invitation credentials and need the same access restrictions as the instance.
